# Interactive Working Memory

Interactive Working Memory is one persistent local app backed by a JSON daily archive.

## Run The Studio

From the source workspace:

```bash
cd apps/working-memory-viewer
npm run dev
```

From the packaged `working-memory` skill:

```bash
scripts/ensure-studio.sh
```

Open:

```text
http://localhost:3020/studio
```

`/studio` loads the current day in the configured timezone. Use an explicit date to inspect or edit a specific archived day:

```text
http://localhost:3020/studio?date=YYYY-MM-DD
```

If the selected day has no `day.json`, or if `day.json.lifecycle.morningRunAt` is missing, the studio should warn that Good Morning has not run for that day. Quick captures can still be saved, but the day should not be treated as a completed morning plan until the working-memory morning flow writes the archive.

## Archive Layout

```text
{interactive-memory-dir}/
  _index.json
  _settings.json
  YYYY-MM-DD/
    day.json
    calendar.json
```

`day.json` is the task/source-of-truth file. It also contains first-class `trackers[]` records for other people's work that may span multiple days, `breaks[]` for lunch/rest blocks, task-level `agentName`, agent-readiness metadata for copyable work orders, and optional `agentRuns[]` metadata on tasks that were deployed to Claude. `calendar.json` is generated by the working-memory morning scan from the Google Calendar connector. `_settings.json` stores the board-wide copy prompt template. `_index.json` is the root navigation/history index for available dates and freshness state.

The studio writes task edits back to the selected date's `day.json`. Working-memory agents write today's `day.json`, today's `calendar.json`, and root `_index.json` during the morning flow.

Default archive paths are portable:

- `WORKING_MEMORY_ROOT_DIR` controls the source workspace root when the app is run from a project checkout.
- `INTERACTIVE_MEMORY_DIR` controls the Interactive Working Memory archive directory.
- If `INTERACTIVE_MEMORY_DIR` is unset, the app uses `${XDG_DATA_HOME:-$HOME/.local/share}/working-memory/Interactive Working Memory`.
- `WORKING_MEMORY_TIMEZONE` controls the day boundary; otherwise the app uses the host timezone.

Past `day.json` files are retained indefinitely. They are used for carry-forward, tracker history, and day history; do not delete old date folders as cleanup. If `_index.json` is missing or stale, it can be rebuilt by scanning date folders that contain `day.json`.

## Trackers

Trackers are separate from tasks. Use them for work owned by someone else where the user wants visibility over multiple days: who owns it, what they are working on, when tracking started, the original ask date, current status, and short notes.

Tasks may link to trackers with `trackerIds` when the user has an action today, such as reviewing the tracked work or sending a follow-up. The tracker itself remains in `day.json.trackers[]` until it is marked `done` or `dropped`.

The Studio header includes a `Capture` button. It opens a modal with `Task` and `Tracker` tabs:

- `Task` capture writes schema v8 task fields directly, including `ticketFields`, `sourceRefs`, `workDepth`, `estimateMinutes`, `agentName`, and computed readiness.
- `Tracker` capture writes a normal `trackers[]` record with person/team, work, status, original ask date, notes, and source refs.

The tracker panel is collapsible. The collapsed state keeps the tracker count visible; the expanded state shows newest-created trackers first in a fixed-height scroll region.

## Calendar Population

The studio does not use local Google OAuth. Calendar events are pulled by Claude Code through the Google Calendar connector during the working-memory morning flow, then written into `calendar.json`.

The calendar panel's `Reload` button re-reads `calendar.json` from disk. Use it after the morning scan or any connector-backed update.

`calendar.json` intentionally avoids full event descriptions because those can contain sensitive agenda notes, dial-in details, or copied email content.

## Prompt Schema

The copy-agent prompt is generated from `task.ticketFields` when the user clicks `Copy prompt`. The app still supports the `{{ticketBody}}` prompt-template placeholder, but that value is rendered on demand and is not stored on the task.

Task readiness values:

- `ready`: copy prompt is directly delegable.
- `warning`: copy is allowed after confirmation and includes missing pieces.
- `incomplete`: capture-only; the app copies a capture summary, not an executable agent prompt.

Schema v8 deploy/text fields:

- `agentName`
- `ticketFields.objective`
- `ticketFields.background`
- `ticketFields.sourcesOverride`
- `ticketFields.constraintsNonGoals`
- `ticketFields.doneWhen`
- `ticketFields.verification`

The generated `ticketBody` structure is:

- Objective
- Background
- Sources
- Constraints / Non-goals
- Done When
- Verification
- Estimate

New saves should not contain legacy `brief`, `rawThoughts`, or stored `ticketBody` task fields. Older archives are migrated into `ticketFields` when loaded.

The prompt template lives in `_settings.json` and can use these placeholders: `{{title}}`, `{{ticketBody}}`, `{{sources}}`, `{{kind}}`, `{{workDepth}}`, `{{estimateMinutes}}`, `{{readinessWarnings}}`, and `{{project}}`.

## Agent Deploy

The ticket modal keeps `Copy prompt` and also supports direct Claude background deployment for ready tasks.

- `Deploy Sonnet` launches the generated prompt with `claude --bg --model sonnet`.
- The split-button menu also offers `Deploy Opus` and `Deploy Haiku`.
- Direct deploy is disabled by default in portable installs. Set `WORKING_MEMORY_ENABLE_DIRECT_DEPLOY=true` to allow the app to launch `claude --bg`.
- Deploy is disabled unless the task is `agentReadiness: "ready"`.
- Deploy runs from `WORKING_MEMORY_AGENT_CWD` when set, otherwise from `WORKING_MEMORY_ROOT_DIR` or the app process directory.
- Deploy uses the task's editable `agentName` as the Claude background agent name.
- The app saves any pending ticket edits before launch.
- The task is marked `in_progress` only after `claude --bg` exits successfully.
- A successful launch appends task-level `agentRuns[]` metadata: model, agent name, launch cwd, launch time, status, and prompt hash.

The full prompt text is not stored in `day.json`.
